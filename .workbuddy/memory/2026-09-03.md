## v31 「图片没改啊」= 浏览器缓存踩坑（重要经验）
- **症状**：v30 复制了 4 张新图覆盖 campus1-1.jpg~4.jpg，文件时间戳是 Sep 3 13:02、内容（VCT 无畏巡回广州合照等）也对，但用户反馈「图片没改啊」还是看到旧图。
- **根本原因**：图片文件名没变（仍是 `campus1-1.jpg`），浏览器看到「URL 没变」就直接用了硬盘缓存里的旧字节，不会重新请求 web server。**浏览器缓存策略是 URL-based，不是文件内容-based**。
- **修复**：在 HTML 模板渲染 `<img src>` 时统一拼接 `?v=2` 缓存破坏参数。改了 4 处：
  1. `renderCampus` 里 carousel 模板：`src="' + src + '"` → `src="' + src + '?v=2'"`
  2. extension-card 模板：`<img src="' + item.extension.image + '"` → `+ '?v=2"`
  3. `openLightboxSingle` 里 `LB.imgs = [src]` → `[src + '?v=2']`
  4. `openLightboxSingle` 里 `lbImg.src = src` → `src + '?v=2'`
- **教学要点（高优先级，下次复用）**：
  - **图片替换后用户说「没改」= 八成是缓存**。先确认文件实际被覆盖（`ls -la` 看时间戳、内容 Read 一眼），再用缓存破坏参数。**别先怀疑脚本没执行**。
  - **缓存破坏三姿势**：
    - ① URL 加 `?v=N`（最稳，推荐）
    - ② `<meta http-equiv="Cache-Control" content="no-cache">`（依赖浏览器支持）
    - ③ 告诉用户按 Ctrl+F5（最差，每次都要用户手动）
  - **改 src 拼接时要 4 处全改**：carousel 渲染、extension 渲染、lightbox 单图打开、lightbox imgs 数组。漏一处就出现「页面是新图、点开放大是旧图」的尴尬情况。
  - **「Write 写文件成功但 ls 找不到」是相对路径冲突**：刚才 Python 写临时 `_check.js` 时 cwd + 绝对路径拼错了，genie-trash 都报双重路径。**保险写法**：只用一个绝对路径，避免 cwd 影响。

## v33 缓存版本号 v2→v3（第 5 张还是旧图的根因）
- **症状**：v32 用 Copy-Item 换了 campus1-5.jpg 内容（文件已更新），但用户仍看到旧图。
- **根因**：v31 加 `?v=2` 时，浏览器第一次加载 `campus1-5.jpg?v=2` 拿到的是**旧图**并缓存了。v32 换文件内容后 URL 还是 `campus1-5.jpg?v=2`，浏览器判定「URL 没变」→ 继续用缓存旧图。**缓存破坏参数的版本号必须跟着「内容变化」递增，而不是跟着「文件覆盖」递增**。
- **修复**：`?v=2` → `?v=3`（replace_all 全换 4 处）。以后每次批量换图，把 `?v=N` 的 N 递增 1。
- **教学要点（高优先级，纠正 v31 的认知）**：
  - v31 记的「加 ?v=2 就能绕过缓存」只对**首次加参数那一次**有效。之后**每次内容变化都要把版本号 +1**，否则又会踩「URL 没变 → 缓存」的坑。
  - **正确的心智模型**：`?v=N` 是一个「内容版本号」，N 变了浏览器才认为资源变了。换一次图 → N+1。
  - **更省事的替代方案**：用「图片文件修改时间」当参数（如 `?t=` + 服务器返回的 mtime），但静态服务器（python http.server）拿不到 mtime 注入，所以手写版本号最实用。

## v35.1 拼图排版修复（缩略图黑底留白）
- **用户反馈**：「这个排版太奇怪了，点进去看也是」——发了两张图，缩略图只占顶部一小条、下面大片黑底（且带"↓下滑查看全文"的浮标）。
- **根因**：
  - `.extension-preview` 容器 CSS：`height: 360px; overflow-y: auto; background: #2a2218`（line 753-767）
  - `.extension-preview img` 是 `width: 100%; height: auto` —— 图片按宽度填满，等比缩高度
  - 第一版拼图是 3×2 = 3840×1480（宽高比 2.6:1）→ 缩到预览列 400 宽 → 高仅 154px，剩 206px 全是黑底 + sticky 的"下滑查看全文"标签
- **修法**：拼图比例改成 **2 列 3 行 = 2560×2160**（接近正方形，宽高比 1.18:1）→ 缩到 400 宽 → 高 337px，几乎填满 360 容器，黑底消失。
- **关键经验（可复用）**：
  - **`width:100% height:auto` 的容器 = 容器尺寸决定缩略图比例兼容性**。缩略图宽高比必须和容器宽高比接近（最好略大于），否则大量留白。
  - **怎么算合不合适**：容器高 H px，宽 W px → 缩略图原比例 P:1 → 缩到 W 宽后高 = W/P。W/P 应在 [0.7H, 1.0H] 区间。这次容器 360 高、400 宽 → 拼图最佳比例 400/(0.7×360) 到 400/360 = 1.59:1 到 1.11:1 之间 → 我选了 1.18:1。
  - **拼图比例选型决策树**：
    - 多张同类截图 + 信息密度高 → 横向拼图（3×2 / 4×3）适合灯箱全屏
    - **多张同类截图 + 要进窄列缩略图 → 竖向拼图（2×3 / 3×4）填满容器**
    - 拼图比例极端（>3:1 或 <0.5:1）会出现严重 letterbox 黑底
  - **`object-fit: cover` 是治标不治本的下策**：会让内容被裁切（这次 5 张图里有"印记 11/4"等关键数字），信息丢失。换比例才是正解。
  - **"下滑查看全文"的 sticky ::after 是为了长截图设计**：单图缩到 225 高时容器剩 135px，提示用户可滚动看到全图。拼图填满容器后这个提示变成噪声（用户根本不用滑），但因为是 ::after 伪元素不影响功能，暂不删。
